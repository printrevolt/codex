# Pipelines Components (Schema "2"): Spec + Usage + Summary

This document is the implementation-aligned specification for **reusable pipeline components** in this fork.

Source of truth:
- Pipeline engine + component expansion: `codex/codex-rs/crates/pr_pipelines/src/lib.rs`
- Headless CLI surface: `codex/codex-rs/crates/pr_cli/src/lib.rs`
- Bundle locations, precedence, and trust model: `PrintRevolt-Codex-CLI-Fork-LLD.md`

## Context

Pipelines are deterministic, typed orchestration defined in `pipelines.json`. Schema `"2"` adds **components** so you can define reusable part lists once and reference them from multiple workflows/pipelines.

Design goals:
- Reuse without introducing a general-purpose scripting language.
- Deterministic, reviewable expansion (no hidden runtime behavior).
- Safe-by-default: global/starter-generated pipelines should not become active without explicit enablement.

Non-goals (current implementation):
- Conditional branching DSL, triggers, or transitions in the bundle format.
- Runtime component evaluation.

## Bundle Format

Pipelines bundles exist at two scopes:
- Global: `<CODEX_HOME>/printrevolt/pipelines.json`
- Project: `<repo_root>/.codex/printrevolt/pipelines.json` (loaded only when repo is trusted/allowlisted)

Schema `"1"`:
- `{ "schema_version": "1", "pipelines": { "<id>": { id, name, enabled, pipeline } } }`

Schema `"2"`:
- `{ "schema_version": "2", "components": { ... }, "pipelines": { ... } }`

### Schema "2" Top-Level

```json
{
  "schema_version": "2",
  "components": {
    "<component_id>": {
      "params": {
        "<NAME>": { "default": "<string>" }
      },
      "parts": [
        { "part_kind": "run_command", "cwd": ".", "argv": ["npm", "test"] }
      ]
    }
  },
  "pipelines": {
    "<pipeline_id>": {
      "id": "<pipeline_id>",
      "name": "Verify",
      "enabled": false,
      "pipeline": { "entry": "main", "workflows": { "main": { "parts": [] } } }
    }
  }
}
```

Notes:
- `pipelines` is a map keyed by pipeline id. The map key and `entry.id` should match.
- `enabled` defaults to `true` in the schema, but **starter drafts generated by this fork set `enabled=false`**.

### `use_component` Part

Schema `"2"` introduces:

```json
{ "part_kind": "use_component", "id": "<component_id>", "args": { "NAME": "value" } }
```

`use_component` is not executable directly.
- The engine rejects it at runtime: it must be expanded into concrete parts before execution.
- The CLI can expand it for preview via `codex-pr pipelines show --expanded --json`.

## Expansion Semantics (Compile-Time Macros)

Components behave like deterministic macros:
- Expansion is recursive (components can use other components).
- Expansion is cycle-checked.
- Expansion is bounded by limits.

### Params, Defaults, and Args

`components.<id>.params` declares parameters. Each param may have an optional `default`.

When expanding `use_component`:
1. Start with all param defaults.
2. Overlay `use_component.args` (call-site args).
3. Validate all required params are present (either default or call-site).

### Component Arg Rules

Component arg values MUST be literal strings:
- Args may not contain `${...}` (any `${` is rejected).

Rationale:
- Component args are intended as compile-time configuration (like selecting `npm` vs `pnpm`), not runtime templating.
- Runtime templating in pipelines (`${var.*}`, `${fact.*}`, `${session_id}`, etc.) is handled separately during pipeline execution.

### `${param.<NAME>}` Substitution

During expansion, `${param.<NAME>}` is substituted into many string fields inside component parts, including:
- `run_command.cwd` and `run_command.argv[*]`
- `require_approval.prompt`, `require_approval.remediation[*]`
- `extract_value` fields (`json_path`, regex `pattern`, `output_key`)
- `assert_fact` fields (`key`, `equals`, `matches_regex`)
- `ensure_worktree` fields (`worktree_root`, `naming`, `branch_name`)
- `ensure_branch` fields (`branch_name`, `protected_branches[*]`)
- `set_var.key`, `set_var.value`
- `fail.message`
- nested `defer` parts
- `run_tool` only for `local_shell` tool input (`command[*]`, `workdir`)

Only `${param.<NAME>}` is substituted at expansion time. Other `${...}` placeholders are left untouched for runtime templating.

## Runtime Templating vs Component Substitution

There are two distinct placeholder systems:

1) Component substitution (compile-time)
- Placeholder: `${param.<NAME>}`
- Source: `use_component.args` plus component param defaults
- Happens: during `use_component` expansion (before execution)
- Supported in: many string fields including `run_command.argv[*]`

2) Pipeline runtime templating (execution-time)
- Placeholder: `${session_id}`, `${task_id}`, `${turn_id}`, `${var.<NAME>}`, `${fact.<KEY>}`
- Source: pipeline run context, config vars, and facts produced during the run
- Happens: during pipeline execution for a subset of string fields
- Not supported in: `run_command.argv` (argv is treated as already-canonical)

### Expansion Limits

Expansion is bounded by default limits:
- `max_depth = 8`
- `max_expanded_parts = 5000`
- `max_total_string_bytes = 1_000_000`

If a limit is exceeded, expansion fails with a structured error (for example `ExpandLimitsExceeded`).

## Precedence, Scoping, and Trust

### Pipeline Entry Precedence

When computing the effective pipeline set:
- Project pipelines override global pipelines by pipeline id.

### Components Precedence

When expanding a pipeline, components are merged by id:
- Global components are loaded first.
- Project components overlay/override global components with the same id (when project scope is in use and the repo is trusted).

### Trust Model (Project Scope)

Project bundles are treated like repo templates/command catalogs:
- They are ignored unless the repo root is allowlisted in `printrevolt.hooks.trusted_repo_roots`.
- `codex-pr pipelines list|show --json` emits warnings when a project bundle is ignored due to lack of trust.

## CLI Usage

Feature gates:
- Pipelines functionality is gated by config: `[printrevolt.pipelines] enabled = true|false`
- Individual pipeline entries are gated by `pipelines.<id>.enabled = true|false`

Core commands:

```bash
# List effective pipelines from global/project (project requires trust).
codex-pr pipelines list --scope both
codex-pr pipelines list --scope both --json

# Inspect a pipeline entry.
codex-pr pipelines show --scope both --id verify --json

# Expand components (schema "2") for inspection/validation only (no execution).
codex-pr pipelines show --scope both --id verify --expanded --json

# Generate a starter Verify pipeline draft (writes schema "2" and sets enabled=false).
codex-pr pipelines draft --scope global --apply

# Enable/disable pipelines feature gate in config.
codex-pr pipelines enable  --scope global
codex-pr pipelines disable --scope global
```

## Example: Reusable Verify Part

`pipelines.json`:

```json
{
  "schema_version": "2",
  "components": {
    "verify.pm_test": {
      "params": { "pm": { "default": "npm" } },
      "parts": [
        { "part_kind": "run_command", "cwd": ".", "argv": ["${param.pm}", "test"] }
      ]
    }
  },
  "pipelines": {
    "verify": {
      "id": "verify",
      "name": "Verify",
      "enabled": false,
      "pipeline": {
        "entry": "main",
        "workflows": {
          "main": {
            "parts": [
              { "part_kind": "use_component", "id": "verify.pm_test", "args": { "pm": "pnpm" } }
            ]
          }
        }
      }
    }
  }
}
```

Preview the expanded form:

```bash
codex-pr pipelines show --scope both --id verify --expanded --json
```

## Summary (Decisions + Guarantees)

- Components are **compile-time macros** expanded deterministically (cycle-checked, bounded).
- `use_component` is **invalid at runtime** and must be expanded before execution.
- Component args are **literal strings** (no `${...}`) to avoid mixing compile-time args with runtime templating.
- `${param.<NAME>}` substitution is for compile-time composition; runtime `${var.*}` / `${fact.*}` / `${session_id}` placeholders remain a separate mechanism.
- Global/project support is uniform:
  - both scopes can define pipelines and components
  - project scope is trust-gated
  - project overrides global by id
